# 质量评分

用这份文档按产品区域和架构层次记录当前质量水位，方便持续知道最薄弱的地方在哪。评分不是展示板，每个低分项都必须能落到下一步行动、验收方式和债务追踪。

## 建议的评分标准

- `A`：覆盖完整、行为稳定、文档清楚、运行风险低。
- `B`：整体可接受，但还有明确短板。
- `C`：能用，但需要针对性补强。
- `D`：脆弱、缺少规范，或很多行为尚未定义。

## 初始模板

| 区域 | 评分 | 原因 | 下一步 | 验收方式 |
| --- | --- | --- | --- | --- |
| 产品面 | C | 有最小需求生命周期示例，但还没有真实产品定义。 | 明确第一个真实用户路径和验收标准。 | `docs/product-specs/` 中存在真实需求文档。 |
| Harness 流程 | B | 已有五阶段流程、门禁、Skill/Command 入口和 CI 骨架。 | 根据真实项目补充更精确的门禁。 | `make ci` 覆盖新增门禁。 |
| 上下文治理 | B | 已有 `context/` 三层入口和服务矩阵示例。 | 替换示例项目上下文，补真实模块知识。 | Agent 能从 `context/project/INDEX.md` 找到项目入口。 |
| 架构文档 | C | 有基础骨架，但还没替换成项目真实信息。 | 补齐 `docs/ARCHITECTURE.md`。 | 架构文档覆盖运行拓扑、包边界和数据流。 |
| 测试 | C | 有模板级 CI、矩阵校验和初始化 smoke test，还没有项目业务测试。 | 接入项目自己的最小 smoke path。 | `make ci` 包含项目级验证命令。 |
| 可观测性 | D | 还没有日志、指标、链路的约定。 | 明确本地和 CI 怎么访问观测数据。 | `docs/RELIABILITY.md` 记录观测入口和排障路径。 |
| 安全 | C | 默认约束和供应链控制已存在，但具体实现还没落地。 | 根据项目接入真实认证、密钥和依赖治理。 | 安全文档覆盖项目实际数据和外部集成。 |

## 与技术债的关系

- 评分为 `C` 或 `D` 的区域，必须在 `docs/exec-plans/tech-debt-tracker.md` 中有对应后续动作。
- 当某项债务关闭时，同步更新这里的评分、原因和验收方式。
